# NotesTaking App — instructions for coding agents

**Current mandatory multi-chat protocol:** [three GPT contributors, A-Z five-task batches and resilient CI](docs/github/THREE_GPT_APK_WORKFLOW.md). Every new or replacement ChatGPT contributor must read [the complete A-Z task list](docs/github/APK_BATCH_A_TO_Z.md), [the machine task catalog](docs/github/APK_BATCH_TASKS.json), [starter prompts](docs/github/THREE_GPT_CHAT_STARTERS.md), and live `python tools/agents/triad.py status` before any claim or edit. These rules supersede the older *two-chat* setup for all new work. Also read [the local-first parallel workflow](docs/github/LOCAL_FIRST_PARALLEL_WORKFLOW.md) and [the batched CI policy](docs/github/BATCHED_CI_POLICY.md).

**Optional local autonomous runner:** [A/B/C headless auto-dispatcher](docs/github/AUTO_DISPATCHER.md) is opt-in only. It cannot wake ChatGPT browser conversations. Never start it with existing browser sessions; explicit exclusive auto-* session replacement, valid coding-model authentication and clean worktrees are required. It cannot approve CI/device QA or publish.

**Three GPT LocalMCP slots:** Chat A, Chat B and Chat C work only in their separately pinned `.agent-worktrees/chat-a`, `chat-b`, `chat-c` checkouts. Their file ownership is exclusive and checked by `tools/agents/check_lane.py`. A successor chat **replaces** its old session via `triad.py replace` before editing; never start two writers in one slot. The old A/B coordinator and historical Gemini Quick Scratch worktree are preserved. By explicit user request on 2026-11-16, NP-004 was reassigned to Chat A through a separately reviewed planning-catalog migration; Gemini must not edit NP-004 concurrently. This task routing does not expand Chat A's file ownership. The top-level checkout is reserved for one locked coordinator integration; workers never push.

- **Never wait for GitHub CI to finish before starting the next independent local task.** CI gates publishing, merging, and releases; it is not a gate for source editing. Check CI briefly at the beginning/end of a turn, then do real local work. In particular, a legacy `LANE-B: review` locks *that checkpoint's approval*, not unrelated A-Z coding: the next task uses the new `triad.py claim` in the same clean B worktree while keeping the legacy handoff SHA as an ancestor. Only release the old review state after exact-SHA CI approval; never alter another writer's files.
- Work in small, clearly scoped **local branches**, especially when a ready PR is currently building. Do not add unrelated commits to a branch under GitHub verification. A dependent branch may start at that PR's exact head; reconcile it onto `main` after the PR merges.
- **Do not push every commit.** Commit useful local checkpoints. Push a coherent, reviewed batch once, normally after the prior GitHub CI checkpoint completes, and record the exact SHA. Do not trigger an extra expensive build just to measure progress. No direct unverified pushes to `main`.
- On this Windows computer, **never run Gradle, Kotlin tests, Android lint, NDK/CMake builds, APK builds, or device installs**. Allowed: source inspection, edits, Git operations, and source-only Python/YAML/resource/diff checks. Actual builds and executable tests run only on GitHub Actions.
- Before editing, inspect callers, resources, tests and data compatibility. Do not change `.xnote`, `.xcanvas`, `.xtemplate`, original license/NOTICE, private notes, and drawing/storage behavior casually. The historical 45 audit findings are **Open** until real acceptance evidence supports closure.
- On each `next` or `proceed`: confirm the active session and claims, atomically claim the highest-priority eligible A-Z task for your slot, implement the bounded source/test change, run permitted checks and hand off a local commit. Exactly **five task cards form one review batch**; later independent tasks may start immediately while earlier CI runs or network is down. **Any A/B/C chat may exclusively claim a CI incident** for diagnosis, but may only edit its own files unless the coordinator allocates a precise shared-path fix. Only the one locked coordinator publishes; CI gates publication, not local coding. Publishing an unrelated coordinator change does not require other workers to stop editing or have clean worktrees; check for real path overlap instead.
- Distinguish **implemented locally**, **pushed**, **cloud CI passed on exact SHA**, **device verified**, and **merged**. Never conflate these statuses. Do not promise unattended background work. For A-Z batches, use `triad.py verify` after exact-SHA CI and applicable QA; the coordinator automatically checks `[x]` in [the batch progress checklist](docs/github/APK_BATCH_PROGRESS.md) and [the A-Z task list](docs/github/APK_BATCH_A_TO_Z.md) when all five tasks are resolved. Workers must not manually tick or claim CI/device acceptance.

Keep the untracked `.kotlin/` folder untouched unless the user separately authorizes cleanup.
